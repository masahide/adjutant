# claudecode からのフィードバック

⏺ Gemini のまとめは議論の合意を正確に反映しており、全体として良い最終案です。

実装に移る前に、この最終案に対して 補足すべき3点 と 1つの懸念 を指摘します。

---

補足すべき点

1. グローバル並行キューの溢れ処理

層3 で maxConcurrent=3 としているが、3スロット全て埋まっている状態で DM が来た場合の挙動が未定義。

選択肢:

- 待機: DM がチャンネル処理の完了を待つ（DM の即時性を損なう）
- プリエンプション: 最低優先度の実行中タスクを中断して DM を割り込ませる（中断されたタスクの状態管理が複雑）
- スロット超過許可: DM/メンションは maxConcurrent の例外として +1 枠を許可（実質 maxConcurrent=4 になりうる）

MVP では 3つ目の「DM は例外枠」 が最もシンプル。仕様に明記すべき。

2. v1.0 → v1.5 のマイグレーション

timeline.jsonl のスキーマ変更（sessionKey 必須化）は既存データとの互換性を壊す。

必要な対応:

- 既存レコード（sessionKey なし）は Flusher/Heartbeat が「unknown session」として扱い、旧ロジック（グローバル境界）でフォールバック
- watermarks.json は新規ファイルなので初回起動時に空で生成
- 新レコードのみ sessionKey を持つため、一定期間は旧レコードと新レコードが混在する

これは仕様書の §5.10（起動時復旧手順）に追記が必要。

3. 設計判断の検証指標

1つの懸念: 層2 の confidence 閾値

Gemini 案で confidence < 0.7 → note 扱い としているが、confidence の信頼性自体が未検証。

LLM の self-reported confidence は実際の正答率と相関しないことが知られている（calibration の問題）。gpt-4o-mini が confidence: 0.85
と返しても、実際の判定精度が 85% とは限らない。

MVP での現実的な扱い:

- confidence 閾値は設定可能にする（既定 0.7）
- 実運用のログから confidence vs 実際にユーザーが反応したか の相関を見て閾値を調整
- 相関が弱ければ confidence を無視して action のみで判定する方向に切り替え

結論

Gemini の最終案をベースとして、上記3点の補足を加えれば実装着手可能な状態。

次のステップの優先順位:

1. データモデル変更: timeline.jsonl の sessionKey 追加 + watermarks.json の型定義（最も影響範囲が広く、他の全ての層が依存）
2. 層0-1 の実装: ルールベース判定 + アテンションウィンドウ（LLM 不要、単体テスト可能）
3. 層2 のプロンプト設計: Route LLM の System Prompt + report_route_decision ツール定義
4. 層3-5 の順次実装
