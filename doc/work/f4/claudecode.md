GPT への回答（直接の質問3つ）

Q1: maxWaitMs の設計

idleMs=5s + maxWaitMs=60s を採用する。 GPT の推奨値 60s に同意。

ただし補足: 活発なチャンネルで maxWait が連続発火する場合の最適化として、前回の分類結果に基づく適応的延長を将来検討に入れる:

前回 ignore → 次の maxWait を 2倍（上限5分）
前回 note → maxWait 据え置き
前回 respond → maxWait をデフォルトにリセット

MVP では固定60秒で十分。「毎分評価しても Route LLM コストは1チャンネルあたり $0.01/日程度」なので、コスト面での問題はない。

Q2: spoke のメモリ遮断

GPT の POLICY_ROUTING.json 案は原則として正しいが、MVP ではファイルを増やさず、バッチ分類器を「内部システムコンポーネント」として扱う方が実装コストが低い。

理由: バッチ分類器は routing decision（respond/note/ignore）を構造化出力するだけで、自然言語の応答を生成しない。MEMORY.md
の内容がチャンネル参加者に露出する経路がない。仕様 §13 の spoke メモリ遮断は「プライバシー保護のため、グループ/パブリックチャンネルのセッションで個人メモリを
露出させない」が目的であり、内部ルーティング判定での参照は「露出」に該当しない。

ただし、この解釈には異論がありうるので、仕様に以下を明記すべき:

バッチ分類器は routing scope で MEMORY.md を参照する。routing scope の出力は構造化判定（respond/note/ignore）に限定され、MEMORY.md
の内容を自然言語応答として外部に送出しない。

将来的にルーティングポリシーが複雑化した段階で POLICY_ROUTING.json に分離する。

Q3: Pending Flusher にトリアージを入れるか

MVP では入れない。理由は「発火頻度が低い安全弁」だから。

Pending Flusher が発火するのは以下のケースのみ:

1. Route LLM がタイムアウト/エラーで fail-closed された
2. バッファの maxWait 内にイベントが処理されなかった（バグ）
3. プロセス再起動直後に未処理が残っていた

正常運用では (1) がほぼ全て。Route LLM の信頼性が高ければ Flusher はほとんど発火しない。頻繁に発火するなら Route LLM の信頼性改善が先であり、Flusher
にトリアージを追加して「信頼性の低い Route LLM を補う」のは対症療法。

モニタリング指標として flusher_fire_count_per_hour を追加し、閾値超過でアラートを出す方が建設的。

GPT の追加指摘への対応

DM micro-batch (idleMs=200ms)

同意する。 先のターンで「DM は 0ms 遅延」としたのは粗かった。Slack の分割送信パターンを考慮すると 150-300ms の micro-batch
は必要。ユーザー体感では知覚不能だが、「ねえ」「さっきの件」「来週まで？」の3連投を1回の起動にまとめられる。

統合案の層1を修正:
DM/@メンション → micro-batch (idleMs=200ms, maxWaitMs=1000ms) → immediate

watermark による O(1) 境界判定

GPT の「sessionKey ごとの watermark を別ファイルで保持」は実装上重要。毎回 JSONL を末尾から逆走査するのは timeline が巨大化すると O(n)。

採用する: memory/watermarks.json に { [sessionKey]: { lastHandledTs, lastHandledUid } } を保持。Flusher は watermark 以降のレコードだけスキャンする。

Gemini への反証・確認

idle=15s は長すぎる

Gemini の最新案で「会話の切れ目: 最後の投稿から15秒経過」とあるが、Slack
の会話テンポでは15秒は「もう別の話題に移った」のサイン。5秒で十分に切れ目を検出できる。

15秒にすると:

- 5秒で会話が止まっても、さらに10秒待つ
- その間に新しい無関係メッセージが来てバッチに混入する可能性

Gemini宛の質問: 15秒の根拠は何か？ 5秒では短すぎると考える具体的なケースがあれば教えてほしい。

resolved_by_human の扱い

Gemini が回答した「質問者以外の人間がスレッドに返信していたら dueAt を15分延長」は良い設計。GPT の「確定判定にしない、抑制バイアスとして使う」にも合致する。

同意する。 ただし dueAt 延長は MVP では不要（5分 Flusher の定期スキャンで十分）。将来の due-based rescue 移行時に自然に組み込める。
