# Geminiからのフィードバック

Claude CodeとGPT、両名からの極めて解像度の高いフィードバックに感謝します。システムの実運用に伴う「エッジケース（無限待機、分割送信スパム）」から「リソース枯渇（グローバル並行実行）」まで、MVP（Minimum Viable Product）が直面するであろう致命的な壁が見事に洗い出されました。

特にClaudeの**「グローバル並行実行数の制御（リソース枯渇の防止）」**の指摘と、GPTの**「DMのmicro-batch（分割送信スパムの防止）」**および**「spokeセッションでのMEMORY.md遮断」**の指摘は秀逸です。

私（Gemini）宛にいただいた質問への回答と反証（軌道修正）を行い、これをベースに**「Adjutant v1.5 統合設計案（Release Candidate）」**を定義します。

---

### 1. 質問への回答と軌道修正（Geminiより）

**Q1 (Claude & GPT): デバウンス窓の max-wait（最大待機）と、DMの即時性（micro-batch）について**

- **回答:** 全面的に同意し、私の「一律デバウンス」および「DM遅延ゼロ」の提案を**撤回・修正**します。
- Slackでは「あのさ」「エラー出た」「助けて」と1文ずつ連投するユーザーが非常に多いです。DMを遅延0msにすると重いエージェントが3回連続で起動してしまいます。
- **修正案:** DM/@メンションは `idleMs=200ms` / `maxWaitMs=1000ms` の**micro-batch**を採用します。チャンネルは `idleMs=3000ms` / `maxWaitMs=30000ms`（最大30秒で強制フラッシュ）とし、無限待機を完全に防ぎます。

**Q2 (Claude): Pending Flusher に「トリアージ用LLM」は本当に必要か？**

- **回答:** おっしゃる通り、**不要（オーバースペック）**でした。撤回します。
- 5分間もスレッドが放置（`pending`）されている時点で、それは「AIの介入が期待されている」可能性が十分に高いです。ここでケチって軽量LLMを挟むより、素直にメインエージェントを起動（フルコンテキストで対応）させた方が、実装がシンプルでUXも良くなります。

**Q3 (GPT): 再起動後の永続化（dueAt）と `resolved_by_human` の扱いについて**

- **回答:**
- **永続化:** 複雑な `dueAt` 管理はMVPから落とし、Claude提案の**「ステートレスな5分周期 Flusher ＋ sessionKey単位の Watermark」**に賛同します。JSONLに `sessionKey` を必須化し、起動時にタイムラインを走査すれば状態は復元できるため、これが最も堅牢です。
- **人間による解決の判定:** 確定判定（絶対介入しない）ではなく、**「抑制シグナル（重み付け）」への格下げ**に完全同意します。Slackのスタンプ文化は多様すぎるため、これをトリガーにシステムを強制停止させるのは危険です。

### 2. 最終統合設計案（Adjutant v1.5 Release Candidate）

これまでの全議論、合意事項、そしてセキュリティ（メモリ分離）を統合した最終パイプラインです。

#### 層1: 受信と Micro/Window バッチ（LLMなし）

イベントを受信し、`sessionKey` 単位のバッファに詰めます。

- **Self (自身):** 即座に `drop`。
- **DM / @メンション (Immediate):**
- 条件: `idleMs=200ms` または `maxWaitMs=1000ms`
- 出力: バッチ化後、分類（層2）をスキップして**直接「層3：グローバルキュー（高優先度）」**へ投入。

- **チャンネル / グループ (Accumulate):**
- 条件: `idleMs=3000ms` または `maxWaitMs=30000ms`
- 出力: バッチ化後、**「層2：バッチ分類」**へ。

#### 層2: バッチ分類（Route LLM + ツール呼び出し）

チャンネルでの「会話の塊」に対し、軽量LLM（gpt-4o-mini等）で介入要否を判定します。

- **入力制御:** spokeセッション（グループ/パブリック）の場合、個人の `MEMORY.md` は**絶対に渡しません**。代わりに `POLICY_ROUTING.json`（チャンネルごとの通知頻度・ポリシー設定）のみを文脈として注入します。
- **出力強制:** `report_route_decision(action: "respond" | "note" | "drop", confidence: number)` ツールを強制呼び出し。
- **フェイルクローズ:** `confidence < 0.7` またはパース失敗時は `note` (保留) に倒す。
- **ルーティング:**
- `respond` -> 層3：グローバルキュー（標準優先度）へ。
- `note` -> `system-event-queue` へ（将来の文脈用）。

#### 層3: グローバル並行制御キュー（リソース・API保護）

プロセス全体でのメインエージェントの同時起動数を厳格に管理します。

- **Max Concurrent:** 3（既定値）
- **Priority:** `Immediate (DM等)` > `Flusher (救済)` > `Standard (チャンネル)` > `Heartbeat`
- キューが溢れた場合は、低優先度のリクエストを待機状態に保ちます。

#### 層4: Pending Flusher（5分周期・ステートレス救済）

迷子になった `pending` メッセージを救い上げます。

- 5分ごとに `memory/timeline.jsonl` を走査。
- 境界は**必ず `sessionKey` 単位の Watermark（lastHandledTs）**を使用。
- 未対応のメッセージ群を発見した場合、トリアージLLMを挟まず、直接「層3：グローバルキュー（Flusher優先度）」へ投入。

#### 層5: Deep Heartbeat（30〜60分周期）

純粋な定期自律思考ループです。

- `HEARTBEAT.md` の指示を実行。
- 出力は `report_heartbeat_status(status, reason, notify)` ツールを強制し、文字列マッチを廃止。

### 次のアクションのご提案

アーキテクチャの骨格は、MVPとしてこれ以上ないほど堅牢で現実的なものに仕上がったと考えます。
実装フェーズに進むにあたり、以下のどの部分のコード（または詳細仕様）から書き起こしましょうか？

1. **層1 & 層2 の実装:** デバウンスロジック（`idleMs` / `maxWaitMs`）と Route LLMのツール呼び出し（プロンプト含む）の実装案
2. **層3 の実装:** `Promise` 制御を用いた「グローバル並行制御キュー（優先度付き）」の実装案
3. **層4 の実装:** JSONLと `sessionKey` 別 Watermark を用いた、高速な Pending Flusher の走査ロジック案

どれから着手するか、あるいはまだ見落としている懸念があれば教えてください。
