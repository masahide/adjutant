Gemini案への疑問・反証

Gemini案「デバウンス→Route LLM の順序逆転」について

方向性は正しいが、一律デバウンスの遅延コストを過小評価している。

Gemini は「2-3秒デバウンスしてからバッチ判定」を提案しているが、DM で「サーバー落ちてる！助けて！」という緊急メッセージが来た時に 2-3
秒の遅延を追加する意味はない。

さらに、Gemini の案は全てのイベントに一律デバウンスを適用しており、チャンネル種別や緊急度に応じた差別化がない。

Gemini案への質問: DM の即時性を維持しつつバッチ分類する方法はどう考えるか？ 「DM はデバウンスなし」とすると、DM
は現行と同じく個別判定に戻り、バッチ評価の恩恵を受けられない。

Gemini案「おせっかい問題 — 人間の介入の考慮漏れ」について

問題の所在の指摘は正しいが、解決策が不十分。

Gemini は「他者の返信やリアクションを評価指標に含める」と言っているが、Slack の会話では:

- 解決は暗黙的（会話が自然に止まる）なことが多い
- 同じスレッドで Human B が返信しても、AI への質問が別途残っている場合がある
- ✅ リアクションの意味はチームによって全く異なる

そもそも、エージェントは呼び出された後にこれらの情報を全て見ることができる。問題は「エージェントの判断力」ではなく「不要なエージェント起動のコスト」。Gemini
の提案は起動後の判断改善であり、起動判定の改善ではない。

Gemini案への質問: 「他者が解決済みかどうか」を LLM なしで判定する方法はあるか？ ルールベースで「元の質問者以外が返信 + 一定時間経過 +
追加質問なし」のようなヒューリスティクスの方が、LLM トリアージより安定しないか。

Gemini案「HEARTBEAT_OK の脆さ → Structured Outputs」について

正しい指摘だが、実装制約を考慮していない。

現在のエージェントは pi-coding-agent SDK 経由で動いており、OpenAI の Structured Outputs をそのまま適用できる場所ではない。SDK
のエージェント出力を構造化するには SDK 側の対応が必要。

ただし、トークンベースの判定（HEARTBEAT_OK 文字列マッチ）をやめて、ツール呼び出しベースの判定に切り替えるなら SDK の枠内で実現可能。例えば:

ツール: report_heartbeat_status(status: "no_action" | "needs_attention", reason: string)

エージェントにこのツールを呼ばせれば、文字列マッチの脆さを回避しつつ SDK 互換を維持できる。

Gemini案「動的スケジューリング（pending 発生から15分後に専用チェック）」について

理論上は正しいが、実装複雑性が高い。

イベント駆動の遅延キューは:

- 大量の pending イベントが同時期に発生すると、15分後にチェックが集中する
- キャンセル処理が必要（pending → run に昇格した場合、スケジュール済みチェックの取り消し）
- プロセス再起動時にスケジュールの復元が必要

単純な「5分間隔の pending フラッシャー」の方が実装が簡単で十分に効果的。pending があれば処理し、なければスキップ。最悪の遅延は5分。

両案が共通して見落としている点

1. 「作業単位」の問題

GPT も Gemini も、イベント単位の run/pending 判定を前提として議論している。しかし Slack の会話は「イベントの集合」であり、個別イベントに対して run/pending
を判定すること自体が根本的にミスマッチ。

例: 3分間に5つのメッセージが来るスレッド。現在の設計では5回判定が走り、そのうち何回かが run で何回かが pending
になりうる。しかしユーザーが期待するのは「この会話ひとまとまりに対して1回反応する」こと。

判定の単位を「イベント」から「アテンションウィンドウ（一定時間内のイベント群）」に変えるべき。

2. コストモデルの現実

単一ユーザーの個人アシスタントとして:

- Heartbeat 30分間隔 = 1日約48回のエージェント起動（最大）
- 200メッセージ/日 × Route LLM = 200回の軽量 LLM 呼び出し
- そのうち run 判定 = 50回の重量エージェント起動（仮定）

コストの大部分は重量エージェント起動が占める。Route LLM の最適化（kNN 化、Structured
Outputs）はコスト面ではマージナルな改善。大きなインパクトがあるのは「重量エージェントの不要な起動を減らすこと」。

3. Heartbeat のグローバル境界問題の深刻度

GPT が指摘した sessionKey 不在の問題は、両案とも修正案を出しているが深刻度を過小評価している。現在の実装では:

セッション A (DM): assistant が t=10 に応答
セッション B (channel): user が t=5 に質問投稿（未対応）

Heartbeat の逆走査は t=10 の assistant レコードで止まり、t=5 の未対応 post は永久に検出されない（次に session B
で何かが起きるまで）。これは「取りこぼし防止」という Heartbeat の存在意義を根本から損なう。

統合改善案

両方の案の良い点を取り入れつつ、見落としを補った統合案:

層1: ルールベース即時判定（LLM 不要、0ms）

イベント着信
↓
ルール判定: - self → drop - DM/グループDM + 非self → immediate（即時エージェント起動）- @メンション → immediate - それ以外 → accumulate（蓄積）

DM と @メンション は判定に LLM が不要。ルールで確実に拾う（GPT案A の DM 即時 + Gemini のルールベース要素）。

層2: アテンションウィンドウ（LLM 不要、30-60秒周期）

30秒ごと、セッション単位で: - 蓄積イベント 0件 → スキップ - 蓄積イベントあり + 最後のイベントから N 秒以上経過（会話の切れ目検出）
→ バッチ分類へ - 蓄積イベントあり + まだ会話継続中（N 秒未満）
→ 次のサイクルまで待機

Gemini の「デバウンス先行」を発展させ、会話の切れ目を待ってからバッチ評価する。これにより「5つのメッセージを個別判定」ではなく「1つの会話塊を1回判定」になる。

層3: バッチ分類（軽量 LLM、会話塊単位）

入力: - セッション内の蓄積イベント群（テキスト全体）- 直近の会話サマリ（最新5-10件のトランスクリプト）- ユーザー優先度設定（MEMORY.md の関連部分）

出力（Structured Outputs / ツール呼び出し）:
{
action: "respond" | "note" | "ignore",
urgency: "high" | "normal" | "low",
reason: string
}

respond → エージェント起動
note → system-event-queue に追加（次回エージェント起動時に参照）
ignore → 破棄

GPT案C の Structured Outputs + 私の先の案A の文脈付き分類 + Gemini のバッチ評価を統合。

層4: Pending フラッシャー（LLM 不要、5分周期）

5分ごと、セッション単位で: - タイムライン逆走査（sessionKey 単位の境界）- 未対応 post/reaction/notification を全て検査 - 未対応あり → エージェント起動 - 未対応なし → スキップ

GPT案E の sessionKey 単位判定 + 私の先の案C を統合。Heartbeat から「未処理救済」の責務を分離。

層5: Heartbeat（定期巡回、30-60分周期）

HEARTBEAT.md に指示がある場合のみ実行: - 未処理判定はしない（層4に委譲済み）- 純粋に「定期巡回で気づくべきこと」の確認 - report_heartbeat_status ツールで構造化出力

Gemini の「HEARTBEAT_OK 廃止 → 構造化」を、SDK 互換のツール呼び出し方式で実現。
