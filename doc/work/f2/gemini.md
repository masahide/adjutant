# geminiからのフィードバック

両方のAIエージェント（Claude、GPT）のレビューを拝見しました。どちらもシステムアーキテクチャやUXの観点で非常に鋭い指摘をしており、LLMをシステムに組み込む際の「あるある」な落とし穴を見事に突いています。

これらの案を踏まえ、**「Claude宛の反証と賛同」**、**「GPT宛の反証と賛同」**を整理した上で、両者の強みを融合させた**「さらに堅牢で実用的な改善アーキテクチャ案」**をご提案します。

---

## 1. Claude案への回答・反証

Claude案は「時間軸（タイミング）」と「文脈の欠落」に対する指摘が非常に優れています。

- **激しく賛同する点:**
- **デバウンスの順序逆転（案A）:** イベント単発でLLMを叩くのではなく、「物理的に数秒待って、まとまったテキストにしてからLLMに評価させる」のは、Slackボットにおいて絶対に必要です。
- **Heartbeatの分割（案C）:** 「取りこぼしの回収」と「定期的な自律思考（HEARTBEAT.md）」は全く別の要件です。これを30分周期の1つのバッチに押し込んでいる現仕様はUXを著しく損なうため、分割案は完全に支持します。

- **反証・懸念点:**
- **案Aの「soon (2-5分タイマー)」の実装コスト:** イベントごとに2〜5分の非同期タイマーをメモリ上で管理するのは、プロセスの再起動時やクラッシュ時に状態をロストしやすく、実装が複雑化します。タイマー管理よりも、案Bの「Urgency Score（スコア蓄積）」と案Cの「5分間隔のPending Flusher」を組み合わせる方が、ステートレスで堅牢に実装できます。

## 2. GPT案への回答・反証

GPT案は「システムとしての安全性（フェイルセーフ）」と「データ境界のバグ指摘」が極めて優秀です。

- **激しく賛同する点:**
- **Fail-closed（デフォルト保留）の原則:** 通知システムにおいて `PrimaryClassifier` のデフォルトが `run`（発火）であるのは致命的です。DMやメンション以外は `pending` に倒すという方針は絶対に取り入れるべきです。
- **統合タイムラインの `sessionKey` 欠落バグの指摘:** §3.10で `sessionKey` が記録されていないため、Heartbeatの逆走査が「別チャンネルのAI発言」を境界として誤認するリスクの指摘は鋭く、即時修正が必要です。
- **Structured Outputsの必須化:** 曖昧なJSON出力を許容せず、OpenAIのStructured Outputs等でスキーマを強制するのは運用安定化の要です。

- **反証・懸念点:**
- **kNN（ベクトル検索）によるルーティングの導入（案B）:** 学術的には正しいアプローチですが、現状のシンプルなMVP構成において、全メッセージをリアルタイムにEmbedding化し、SQLite-vecで近傍探索する処理を前段に挟むのは**オーバーエンジニアリング（複雑化・遅延の増加）**の懸念があります。まずは「ルールベース ＋ 軽量LLM」で十分実用レベルに達します。

## 3. 提案：ハイブリッド・アーキテクチャ案（Adjutant v1.5）

両者の良いところ（Claudeの時間制御＋GPTのフェイルセーフ）を統合し、実運用に耐えうる最良のアーキテクチャを提案します。

### ステップ1：ルールベースの即時トリアージ (Fail-Closed)

イベントを受信した瞬間、**LLMを使わずに**決定的（Deterministic）なルーティングを行います。

- **DM または `@メンション`:** 即座に `run` レーンへ（遅延ゼロで対応）。
- **自身の発言 (Self):** 即座に `drop`。
- **それ以外の投稿 (チャンネル/グループ):** 一旦すべて `pending` 扱いとし、**セッションごとのバッファ（デバウンス窓：例 5秒）**に蓄積し、同時に「Urgency Score」を加算します。

### ステップ2：バッチ化された Route LLM (Structured Outputs)

5秒間の沈黙（デバウンス完了）後、またはUrgency Scoreが閾値を超えた場合、バッファに溜まった数件のメッセージを**まとめて** Route LLM (例: gpt-4o-mini 等) に投げます。

- **プロンプトの文脈:** 「以下の連続したメッセージを見て、AIアシスタントが今すぐ介入して返答・作業すべきか判定せよ」
- **出力:** Structured Outputs を使い、以下のJSONを強制します。

```json
{
  "outcome": "run" | "pending",
  "confidence": 0.0 ~ 1.0,
  "reason": "ユーザー同士で完結している会話のためpending"
}

```

- **フェイルセーフ:** タイムアウト時やAPIエラー時、または `confidence < 0.7` の場合は安全側に倒して **`pending`** とします。

### ステップ3：Heartbeat の「2層ループ」化

「未対応の救済」と「定期巡回」の責務を分離します。タイムラインの記録には必ず `sessionKey` を付与し、セッション単位で独立して境界を判定します。

1. **Pending Flusher (5分周期の高速ループ):**

- 過去5分〜15分の間に `pending` に分類されたまま放置されているメッセージをスキャンします。
- ここで初めて「トリアージ用LLM」を呼び出し、「ユーザーが返答を待ちわびているか？」「ただの会話の終わり（了解等）か？」を再評価し、必要ならメインエージェントを起動します。

2. **Deep Heartbeat (30分周期の低速ループ):**

- 未読メッセージの有無に関わらず起動します。
- 純粋に `HEARTBEAT.md` の指示（例：「JIRAの未アサインチケットをチャンネルに通知して」等）を実行するための自律思考ループとして機能します。

### 次のアクション

このハイブリッド案であれば、通知のスパイクを防ぎ（GPTのフェイルセーフ）、文脈を理解したルーティングを実現し（Claudeのバッチ化）、システムの複雑化も最小限に抑えられます。

この設計方針で進める場合、**Route LLM に渡すための具体的な System Prompt と JSON Schema の設計**、または **Pending Flusher の詳細な判定フロー** のどちらかから詳細化していくのが良いかと思います。どちらを先に掘り下げてみましょうか？
