構造的な問題点

1. Route LLM がデフォルト無効で、有効にしても文脈が致命的に不足

ADJUTANT_ROUTE_LLM_ENABLED のデフォルトは 0（無効）。無効時は決定論的ルールで non-self + post →
run（常に即時実行）。つまりデフォルトでは全ての他者投稿が重量エージェントを起動する。

Route LLM を有効にした場合でも、分類器が見るのはこれだけ:

{
"uid": "slack:C123@1234.5678",
"eventKind": "post",
"actor": "U999",
"text": "了解",
"primaryOutcome": "run",
"selfState": "non-self"
}

見えないもの:

- 会話履歴（「了解」が重要な承認の返事か雑談か判断不能）
- ユーザーの優先度設定（MEMORY.md）
- 同一スレッドの前後の文脈
- 他の pending イベントの存在

1000ms タイムアウトで単発イベントを判定するこの設計では、分類精度の天井が構造的に低い。

2. run/pending の二値分類と Heartbeat 30分の組み合わせが不整合

現在の設計のフローを時間軸で見ると:

t=0s イベント着信 → Route LLM "pending" 判定
t=0~30m 何も起きない（放置）
t=30m Heartbeat 起動 → timeline 逆走査 → 15分超の未対応 post 発見
t=30m+ 重量エージェント起動 → ようやく処理

問題: 「FYI だから即時不要」と判定されたものが、最悪30分放置される。ユーザーから見ると「反応しないことがある AI」になる。一方で Heartbeat が拾う保証もない:

- Heartbeat は kind=post しか検査しない（reaction/notification の pending は永久に放置）
- pending-session-backfill に uid があれば Heartbeat も見送る
- HEARTBEAT.md が空なら Heartbeat 自体がスキップ

3. Heartbeat の毎回フルエージェント起動がコスト効率悪い

Heartbeat は30分ごとに重量エージェントを起動する。未対応がなくても HEARTBEAT_OK を返すだけのために:

- コンテキスト組み立て（イベント読み込み + メモリ読み込み + トランスクリプト）
- セッションロック取得
- フルモデル呼び出し

仕様書 §8.2 のタイムライン逆走査で「未対応なし」と判定できるケースでは LLM を呼ばずにスキップできるが、HEARTBEAT.md
に指示がある場合は常に起動する。つまり定期巡回指示を書いた瞬間、30分ごとに確実にフルコスト発生。

4. 分類→デバウンス の順序が逆

現在: イベント着信 → Route LLM 個別分類 → デバウンス(1000ms) → dispatch

Route LLM
は個別イベントを見て判定するが、デバウンスは分類後に行われる。バースト的に届く一連のメッセージを「まとめて見れば重要」と判断できるケースで、個別には全部
pending にされうる。

5. pending 一括回収の信頼性

次に run イベントが来た時に pending を一括回収する設計だが:

システムプロンプトに「未回答の質問や未完了タスクが残っている場合は今回ターンでまとめて回収すること」を明示

これはエージェントの善意に依存している。コンテキスト窓に pending が全部入りきる保証もなく、エージェントが最新の run イベントに注力して古い pending
を見落とすリスクがある。

改善案

案A: 「デバウンス先行 + バッチ分類」に再設計

イベント着信
↓
デバウンス (5-30秒、設定可能)
↓
バッチ分類器（軽量LLM or ルール）
入力: デバウンス窓内の全イベント + 直近会話サマリ + ユーザー優先度
出力: urgent / soon / batch / drop
↓
├→ urgent: 即時エージェント起動
├→ soon: 2-5分タイマー → エージェント起動
├→ batch: 次回バッチフラッシュで処理（5-15分周期）
└→ drop: 破棄

利点:

- 分類器がバッチ全体 + 会話文脈を見るので精度が格段に上がる
- urgent/soon/batch の3段階で「30分放置」問題を解消
- デバウンスが先なのでバースト的メッセージを正しく評価できる

案B: Route LLM を廃止し、ルールベース + 動的スコアリング

イベント着信
↓
ルールベース即時判定 (0ms) - @メンション or DM → urgent (即時) - 優先チャンネル + キーワード → soon (2分) - それ以外 → accumulate
↓
セッション単位アキュムレータ - pending イベント数 × 重み → urgency score - score > 閾値 OR 経過時間 > max_wait → flush
↓
エージェント起動（accumulated イベントを一括処理）

利点:

- LLM 呼び出しゼロでルーティングコスト削減
- @メンションや DM はルールで確実に拾える（LLM より高信頼）
- urgency score で「じわじわ溜まる」ケースも自然に拾える
- Heartbeat は純粋な定期巡回（safety net）に特化できる

案C: Heartbeat を軽量化 + pending フラッシュを分離

現在の Heartbeat が担っている2つの責務を分離する:

[Pending Flusher] 5分間隔 - timeline 逆走査のみ（LLM なし）- 未対応 post + reaction + notification を全て検査 - 見つかったら即エージェント起動

[Heartbeat] 30分間隔（or 1時間）- HEARTBEAT.md の定期巡回指示のみ - 未対応メッセージ検査はしない - 「何も書いてなければスキップ」を維持

利点:

- pending の救済が30分→5分に短縮
- reaction/notification の pending も救済対象に
- Heartbeat のコスト削減（定期巡回が不要なら起動しない）

---

推奨

案A + 案C の組み合わせが最もバランスが良いと考える。

1. Route LLM を「バッチ対応 + 文脈付き」に再設計（案A）
2. Heartbeat と pending フラッシュを分離（案C）
3. Route LLM が不要なケース（@メンション、DM）はルールで即時 run（案B の部分採用）

これにより:

- 即時対応すべきものは確実に拾う（ルール）
- 判断が必要なものは文脈付きで分類する（バッチ分類器）
- 取りこぼしは5分以内に救済する（Pending Flusher）
- 定期巡回は必要な時だけ走る（Heartbeat 軽量化）
