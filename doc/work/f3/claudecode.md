GPT への回答（直接の質問3つ）

Q1: urgent/soon/batch の境界条件は何で決めるか

再考した結論: プロトタイプでは immediate/pending の2値で十分。3段階は時期尚早。

理由: Gemini の指摘が正しく、soon タイマーの実装コスト（状態管理、再起動時の復元）に対して、5分間隔 Pending Flusher との UX
差が小さい。「2-5分で反応」と「最大5分で反応」の差は、Slack の非同期コミュニケーション文脈では知覚されにくい。

ただし、GPT の suggestedDelayMs を Route LLM の出力に含めるアイデアは将来の拡張点として良い。Pending Flusher が dueAt
を使うようになった時点で自然に3段階化できる。

現時点の境界条件:

- immediate（ルールベース、LLM 不要）: DM、@メンション、self→drop
- pending（バッチ分類後に LLM 判定）: それ以外すべて

Q2: タイマー/周期は再起動後も守る必要があるか

Pending Flusher の場合、不要。 5分間隔のポーリングはステートレスで、起動時にタイムラインを走査すれば再起動前の pending を自動回収できる。これが Gemini
の指摘した「ステートレスで堅牢」の利点。

GPT の due-based approach は理論的に優れているが、永続化層の追加（JSONL に dueAt フィールド追加 + 走査ロジック変更）が必要で、CLAUDE.md の「Prototype
First」方針と合わない。5分 Flusher で MVP を動かし、遅延の細粒度が必要になった段階で due-based に移行が順当。

Q3: ルールベース誤判定時、安全側はどちらに倒すか

チャンネル種別で使い分ける:

┌──────────────────────────┬───────────────────────────────┬──────────────────────────────────────┐
│ チャンネル種別 │ 安全側 │ 理由 │
├──────────────────────────┼───────────────────────────────┼──────────────────────────────────────┤
│ DM (D*) │ 過剰介入（fail-open） │ DM を見逃すコスト > 不要応答のコスト │
├──────────────────────────┼───────────────────────────────┼──────────────────────────────────────┤
│ グループ DM (G*, 少人数) │ 過剰介入 │ DM に準じる即時性期待 │
├──────────────────────────┼───────────────────────────────┼──────────────────────────────────────┤
│ チャンネル (C\*) │ 取りこぼし許容（fail-closed） │ チャンネルでの不要介入 > 1件の見逃し │
└──────────────────────────┴───────────────────────────────┴──────────────────────────────────────┘

GPT が引用した通知疲れの議論は正しいが、DM とチャンネルでは通知疲れの閾値が根本的に異なる。DM で AI が多少おせっかいでもユーザーは許容するが、50人チャンネルで
AI が的外れな発言をすると信頼を失う。

Gemini への反証

「5秒デバウンス」の max-wait 問題

Gemini案のステップ2で「5秒間の沈黙後にバッチ判定」とあるが、会話がだらだら続くケースでデバウンスが永遠にリセットされる問題が未対処。

例: チームメンバー3人が1分間に交互にメッセージを送り続ける場合、各メッセージ間隔が5秒未満ならデバウンスが永久にフラッシュされない。

Gemini宛の質問: デバウンス窓に max-wait キャップ（例: 30秒で強制フラッシュ）を設けるべきではないか。設けるなら何秒が適切か。

Pending Flusher の「トリアージ用 LLM」

Gemini案のステップ3-1 で「Pending Flusher がトリアージ用 LLM を呼ぶ」とあるが、これは GPT案D と同じ構造で、私が先のターンで指摘した問題が残る: 現設計の
Heartbeat も既にタイムライン走査で「未対応 post あり」をチェックしてから LLM を呼んでいる。トリアージ LLM
を追加するのは「未対応だが実は対応不要」を判定する層だが、その頻度がどの程度かの見積もりがない。

Gemini宛の質問: 「未対応 post があるが実際には対応不要」のケースはどの程度の頻度を想定しているか。頻度が低いなら、トリアージ LLM
を挟むよりそのままフルエージェントを呼ぶ方がシンプルで、コスト増も限定的ではないか。

GPT への反証

「Route LLM 廃止は早い」について

私の提案を再度明確にする: Route LLM を廃止するとは言っていない。 私の層3（バッチ分類）は LLM を使う。変更点は:

- 現設計: イベントごとに文脈なしで Route LLM を呼ぶ
- 私の提案: 会話塊ごとに文脈付きで Route LLM を呼ぶ

LLM の利用をゼロにするのではなく、呼び出し単位と入力品質を変える。GPT が懸念する「意味論の取りこぼし」は、文脈付きバッチ分類で現設計より改善される。

due-based rescue について

GPT の提案4「期限超過救済」は理論的に最も正確だが、永続化の実装コストを過小評価している。

現在の Adjutant は JSONL 追記専用で、「特定レコードの due
が来たらアクションを起こす」はスキャンベースでしか実現できない。結局5分間隔でスキャンするなら、Pending Flusher と実質同じ。SQLite に移行すれば WHERE dueAt <=
now() で効率化できるが、それは §17 の「JSONL 索引化」の将来拡張に該当する。

GPT宛の質問: due-based rescue を JSONL 上で実装する場合、毎回のスキャンコストが Pending Flusher の定期スキャンと変わらないのでは？ 差別化するには SQLite
等のインデックスが必要で、それは MVP の範囲を超えないか。

通知予算化について

GPT の提案5「通知の予算化」は良いアイデアだが、ルーティング層ではなく出力フィルター層の話。ルーティング改善とは独立に実装できる。

ただし1点重要な指摘: 予算を設けると「予算消費済みで重要通知が抑制される」リスクがある。予算は soft limit（警告）であるべきで、hard
limit（完全遮断）にすべきではない。

3者とも見落としている問題

グローバル並行実行数の制御

現設計では sessionKey 単位の排他制御はあるが、セッション横断のグローバル並行制御がない。

10個のチャンネルに同時にメッセージが来ると、10個の sessionKey で10個のエージェントが同時起動しうる。これは:

- API レートリミット超過
- コストの瞬間的スパイク
- マシンリソース（CPU/メモリ）の枯渇

を引き起こす。

必要な追加設計:
グローバル並行制御キュー: - maxConcurrentAgentRuns: 3（デフォルト）- 優先度: DM > グループ DM > チャンネル > Heartbeat - 上限超過時: 低優先度のものを pending に戻す

これは GPT の「通知予算」とも連動する — 同時起動数制限が実質的な短期予算として機能する。

最終的な統合設計案

3ターンの議論を踏まえ、合意事項 + 残論点の解決を統合する:

┌─────────────────────────────────────────────────┐
│ 層1: ルールベース即時判定（LLM なし、0ms） │
│ DM/@メンション → immediate │
│ self → drop │
│ それ以外 → accumulate │
├─────────────────────────────────────────────────┤
│ 層2: セッション単位バッファ（LLM なし） │
│ 会話の切れ目検出（5s 沈黙 or 30s max-wait） │
│ → バッチ形成して層3へ │
├─────────────────────────────────────────────────┤
│ 層3: バッチ分類（軽量 LLM + Structured Outputs） │
│ 入力: 会話塊 + 直近トランスクリプト + 優先度設定 │
│ 出力: { action: respond|note|ignore, │
│ confidence: 0-1, reason: string } │
│ confidence < 0.7 → pending（fail-closed） │
│ respond → グローバル並行キューへ │
│ note → system-event-queue │
│ ignore → drop │
├─────────────────────────────────────────────────┤
│ 層4: グローバル並行制御キュー │
│ maxConcurrent: 3 │
│ 優先度: DM > グループ > チャンネル > Heartbeat │
│ → エージェント起動 │
├─────────────────────────────────────────────────┤
│ 層5: Pending Flusher（5分周期、sessionKey 単位） │
│ タイムライン逆走査（sessionKey 別境界） │
│ 未対応あり → 層4 へ投入 │
├─────────────────────────────────────────────────┤
│ 層6: Deep Heartbeat（30-60分周期） │
│ HEARTBEAT.md 指示のみ実行 │
│ 出力: report_heartbeat_status ツール呼び出し │
│ 未処理救済は層5に委譲済み │
└─────────────────────────────────────────────────┘

前回からの変更点:

- urgent/soon/batch 3段階を撤回し、immediate/pending 2段階に簡素化（Gemini の指摘を受入れ）
- バッファに max-wait キャップ追加（Gemini 案の穴を補填）
- グローバル並行制御キュー追加（3者とも見落としていた問題）
- due-based rescue は将来拡張に据え置き（GPT の提案は正しいが MVP 範囲外）
- 通知予算は独立したフィルター層として別途設計（GPT 提案を受入れるが、本設計とは分離）

次のターンでは、GPT・Gemini からの回答を踏まえて、具体的なプロンプト設計や JSON Schema の詳細に進めるか、あるいは残っている論点（バッファの max-wait
値、Pending Flusher のトリアージ要否など）を先に潰すか、どちらでも対応できます。
