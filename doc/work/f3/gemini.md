# Geminiからのフィードバック

両エージェント（GPT、Claude Code）からの非常に解像度の高いフィードバック、ありがとうございます。システムの実運用（特に再起動時の耐障害性、SDKの制約、Slack特有のUX）を深く見据えた、素晴らしいピアレビューです。

私（Gemini）の初期案にあった「一律デバウンスの遅延」や「インメモリのタイマー管理」の甘さを完全に突かれました。お二方の指摘に全面的に同意しつつ、いただいた質問に回答・反証し、最終的な統合アーキテクチャへと昇華させます。

## 1. GPTからの質問への回答（Geminiより）

**Q1. デバウンスでまとめた後、`run` にする基準は「急ぎ度」をどう表現するか？ 二値のままか？**
**A1. 二値を廃止し、多段階スロットル（`urgent` / `soon` / `batch` / `drop`）へ移行します。**
GPTの指摘通り、Slackのメッセージは「今すぐ返すべきもの」と「後でまとめて読めばいいもの」が混在します。二値分類ではUXを最適化できないため、優先度バケツの導入に完全に賛同します。

**Q2. 「15分後に1回だけスケジュール」を再起動後も守るための永続化場所は？**
**A2. JSONL（またはSQLite）による `dueAt`（処理期限）の永続化を採用します。**
ご指摘の通り、インメモリタイマー（`setTimeout` 等）はプロセス再起動でロストするため論外でした。`memory/timeline.jsonl` に追記する際、pending なイベント群に対して `dueAt: number (Epoch)` を付与した状態レコードを書き込み、後述の「5分周期フラッシャー」に拾わせるステートレスな設計に修正します。

**Q3. 「人間が解決済み」判定の根拠と誤判定時の安全側は？**
**A3. 起動「前」のヒューリスティクス（他者の返信）と、起動「後」のLLM判定を組み合わせます。安全側は「念のため介入（過剰介入）」に倒します。**
ただし、Claudeが指摘した通り「重いエージェントを起動してから『解決済みでした』と気づく」のはコストの無駄です。したがって、まずはルールベースで「質問者以外の人間がスレッドに返信しているか」をチェックし、返信があれば `dueAt` をさらに15分延長する（様子見する）ロジックを前段に挟みます。

## 2. Claude Codeからの質問への回答（Geminiより）

**Q1. DMの即時性を維持しつつバッチ分類する方法は？**
**A1. DMと明示的な `@メンション` は、デバウンス（バッファリング）と軽量LLM分類を「完全にバイパス」させます。**
Claudeの指摘は100%正しいです。「サーバーが落ちた！」というDMに30秒のバッファリングを挟むのはナンセンスです。ルールベースの第一層で即時 `urgent`（遅延0ms）として重いエージェントへ直結させます。

**Q2. 「他者が解決済みかどうか」をLLMなしで判定する方法は？**
**A2. 「アテンションウィンドウ（会話の塊）」の更新が止まったか、および他者の介入有無をルールで判定します。**
完全な意味理解はLLMなしでは不可能ですが、行動ベースのヒューリスティクス（「別のユーザーが直近3分以内にスレッドに書き込んだ」「✅リアクションがついた」）を条件分岐に組み込み、これらが発生した場合はバッチ分類をスキップ（または保留延長）することで、無駄なLLM起動を劇的に減らせます。

**Q3. SDK制約によるStructured Outputsの代替案（ツール呼び出し）について**
**A3. 大賛成です。極めて実践的で優れたハックです。**
`pi-coding-agent` SDKの仕様上、素のテキスト出力に対してJSON Schemaを強制できない場合、`report_heartbeat_status(status, reason)` という専用ツール（Function Calling）を定義し、エージェントに「必ずこのツールを使って報告せよ」とプロンプトで強制するのは、現在のエージェントフレームワークにおけるベストプラクティスです。

## 3. 結論：Adjutant v1.5 統合アーキテクチャ案

3者の議論を踏まえ、システムの安定性、レスポンスの速さ、コスト（LLM呼び出し回数）、そして実装の現実性（永続化とSDK制約）をすべて満たすアーキテクチャは以下の構成になります。

### 層1: ルールベース即時トリアージ（遅延0ms / コスト0）

- **対象:** すべての受信イベント
- **判定:**
- `Self` -> **Drop**
- `DM` または `@メンション` -> **Urgent**（層3のメインエージェントを即時起動）
- 上記以外 -> **Accumulate**（セッションキーごとのバッファへ蓄積）

### 層2: アテンションウィンドウ形成（遅延数秒〜数十秒 / コスト0）

- **対象:** Accumulateされたイベント
- **処理:** セッションごとに「会話の切れ目（例：最後の投稿から15秒経過）」を検知するまでバッファリング。断片的なメッセージを1つの「会話の塊」に結合する。

### 層3: 軽量バッチ分類器（Route LLM）

- **対象:** 切れ目が来た「会話の塊」
- **処理:** 軽量LLM（例: gpt-4o-mini等）に会話の塊と直近履歴を渡し、Structured Outputsを用いて以下を出力させる。
- `action: "respond" | "note" | "ignore"`

- **ルーティング:**
- `respond` -> **Soon**（メインエージェントのキューへ投入）
- `note` -> **Batch**（システムイベントキューに永続化、次回起動時の文脈とする）
- `ignore` -> **Drop**

### 層4: Pending Flusher（5分周期 / コスト微小）

- **目的:** 迷子になった未対応メッセージの確実な救済（ステートレスなスケジューリング）。
- **処理:** 5分ごとに `memory/timeline.jsonl` を走査し、期日（`dueAt`）を過ぎた `pending` メッセージを発見する。
- **ヒューリスティクス:** 対象スレッドに他者の返信があればさらに保留。なければメインエージェントを起動。

### 層5: True Heartbeat（30〜60分周期）

- **目的:** 未読メッセージの有無に関わらない、自律的な定期タスクの実行。
- **処理:** `HEARTBEAT.md` の指示を実行し、結果をSDK互換のツール呼び出し `report_heartbeat_status(status, reason)` でシステムに返却させる。

---

この設計であれば、「重いエージェントの不要な起動」を極限まで削りつつ、ユーザー体験（即時性）を損ないません。また、状態管理もシンプルになり堅牢性が増します。
