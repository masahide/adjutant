## gemini案

ご提示いただいた「Adjutant 統合仕様書 v1.0」を拝見しました。ブラウザのCDPを利用してSlackのイベントをリアルタイムに傍受し、AIがプロアクティブに動くという野心的なアーキテクチャですね。

LLMの利用箇所である**「Fast Path（軽量LLMによる一次判定）」**と**「Slow Path（Heartbeatによる未処理回収）」**に絞って設計をレビューしました。

率直に申し上げると、システムが目指す「自律的でノイズのないアシスタント」という目的を達成するには、**現在のルーティング順序と判定の粒度にいくつかクリティカルな弱点**があります。Slackという「大量の断片的なメッセージが飛び交う環境」において、この設計では「APIのタイムアウト」や「AIの的外れなおせっかい」が多発する可能性が高いです。

具体的に掘り下げ、改善案を提案します。

---

## 1. Fast Path (Route LLM) の設計レビュー

現在の仕様（§9.2, §9.5, §9.6）では、イベント受信直後に都度 Route LLM で判定し、その後デバウンス（バッファリング）を行っています。

- **現状のフロー:** `イベント受信` → `Route LLMで判定 (run/pending)` → `runならデバウンス` → `ChatHandler`

### 懸念される問題点

1. **APIスパイクとタイムアウトの頻発:** Slackでは1つの文章を複数回に分けて送信するユーザーが多くいます。メッセージごとに Route LLM（最大並列数1、タイムアウト1000ms）を叩くと、一瞬でキューが詰まります。タイムアウト時は一次判定（デフォルト `run`）にフォールバックするため、結果的にデバウンス層へ大量のイベントが流れ込み、ノイズフィルターとして機能しなくなります。
2. **文脈欠落による誤判定:** 「はい」「後で確認します」といった短い単一メッセージだけをLLMに渡しても、それが対応すべきタスク（run）なのか、無視していい相槌（pending）なのか、前後の文脈がなければLLMには判断できません。

### 💡 改善案：順序の逆転とバッチ評価

イベントごとにLLMを叩くのではなく、**「デバウンス（時間窓での物理的結合）を行ってから、Route LLMに判定させる」**設計に変更すべきです。

- **改善後のフロー:** `イベント受信` → `(A) セッションごとにデバウンス (例: 2〜3秒)` → `(B) まとまった文脈で Route LLM 判定` → `(C) runなら ChatHandler`

**具体的な実装のポイント:**

- 数秒間の連続したメッセージ（および直近の履歴数件）をまとめてRoute LLMに渡します。これにより、LLMは「会話のひとまとまり」を見て、AIが介入すべきかを正確に判断できるようになります。
- Route LLM には OpenAI の Structured Outputs（JSON Schema固定）を用い、単なる `run/pending` だけでなく、`confidence` や `reason` を確実に出力させます。

## 2. Slow Path (Heartbeat) の設計レビュー

現在の仕様（§8）では、30分ごとに定期実行し、タイムラインを逆走査して「AIが最後に介入した境界」以降に15分以上経過したユーザーのPostがあれば、LLMを起動して対応要否を判断させています。

### 懸念される問題点

1. **「人間の介入」の考慮漏れ（おせっかい問題）:** AIが介入していないだけで、実は「チャンネル内の他の人間がすでに回答して解決済み」というケースが多発します。未対応（時間経過）というトリガーだけでメインエージェントを自律起動させると、解決済みの話題にAIが蒸し返すように介入してくるリスクがあります。
2. **自然言語マッチングの脆さ:** AIに「対応不要なら `HEARTBEAT_OK` と返せ」と指示し、文字列マッチで通知を抑制する仕様（§8.3）は非常に脆いです。モデルのバージョンアップや気まぐれで `HEARTBEAT_OK. No action needed.` と出力された瞬間、正規表現から漏れてユーザーに不要な通知が飛びます。

### 💡 改善案：状況認識の高度化と動的スケジューリング

Heartbeatを単なる「未対応タイマー」から、**「文脈のクロージング判定機」**に昇格させる必要があります。

1. **出力の構造化 (Structured Outputsの徹底)**
   プロンプトでの `HEARTBEAT_OK` 指示を廃止し、Heartbeatエージェントの出力をJSON Schemaで厳格に定義します。

```json
{
  "status": "resolved_by_human" | "needs_ai_action" | "no_action_needed",
  "reason": "ユーザーBがすでに回答して解決しているため",
  "action_payload": "..." // needs_ai_action の場合のみ生成
}

```

これにより、システム側で確実に後続処理（通知抑制か、自律発言か）をプログラム的に分岐できます。2. **他者の反応（リアクション・返信）を評価指標に含める**
逆走査で集めるコンテキストに、ターゲットユーザーのPostだけでなく、それに対する「他の人間の返信」や「完了を意味するリアクション（✅など）」を明示的に含めます。LLMには「これは誰かが対応済みか？」を判断の第一基準とさせます。3. **ポーリングから動的スケジューリングへの移行（将来検討）**
30分固定の定期巡回ではなく、「`pending` に振り分けられたメッセージが発生した時刻から15分後に、そのスレッド専用のSlow Pathタスクを1回だけスケジュールする」というイベント駆動の遅延キュー構成にすると、無駄な空回り（Heartbeatが空振りするだけの処理）を劇的に減らすことができます。

---

### まとめ

設計思想自体は非常に優れていますが、**「LLMは断片的な情報処理や、厳密な文字列の一致判定には向いていない」**という前提に立ち返る必要があります。

- **Fast Path:** 細かいイベントをLLMに投げる前に、システム側で時間的にデバウンスして「文脈の塊」を作ってからLLMに判定させる。
- **Slow Path:** 自然言語によるフラグ出し（`HEARTBEAT_OK`）をやめ、JSONによる厳格な状態判定に移行する。

この2点を仕様に反映するだけでも、システムの安定性とAIの「賢さ」の体感は劇的に向上するはずです。
