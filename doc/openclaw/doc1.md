# OpenClaw 技術深層解析：第1章

## プロアクティブ・アーキテクチャと実行制御

OpenClaw（旧称：Clawdbot/Moltbot）は、従来の受動的なチャットボット（User-Initiated）のパラダイムを脱却し、環境の変化や時間の経過をトリガーとして自律的にタスクを遂行する「System-Initiated」なエージェント・フレームワークです。
本章では、その能動性を支える「ハートビート機構」「イベント駆動モデル」、そして安全な自律動作を保証する「実行ループとゲートウェイ」の設計について解説します。

### 1.1 設計思想とシステム概要

OpenClawは、Peter Steinbergerによって開発されたセルフホスト型の自律エージェントであり、以下の中心的な哲学に基づいて設計されています。

- **ローカル・ファースト & プライバシー:** ユーザーのハードウェア（macOS/Linux/WSL2）上で常駐プロセスとして稼働し、APIキーやログはローカル環境外に流出しません。
- **能動性（Agency）:** ユーザーの指示待ちではなく、内部タイマーや外部イベントを契機に自らコンテキストを構築し、ツール（コマンド実行、ファイル操作、ブラウザ制御など）を行使します。

### 1.2 ハートビート・メカニズム (The Heartbeat)

エージェントが「生きている」かのように振る舞う核心技術が、定期的な自己覚醒プロセスである「ハートビート」です。

- **基本動作とHEARTBEAT.md**
- ゲートウェイプロセスは設定（`openclaw.json`）に基づき、デフォルトで**30分ごと**（`"every": "30m"`）に内部タイマーを発火させます。
- この際、エージェントは `~/clawd/HEARTBEAT.md` を読み込みます。ここには「緊急メールの確認」「カレンダーの予定チェック」「Gitの未処理PRの確認」といった監視リストがMarkdown形式で記述されています。
- システムはこれを「疑似的なユーザーメッセージ」として扱い、LLMに現在の状況と照らし合わせてタスクの実行要否を判断させます。

- **回転型ハートビート（Rotating Heartbeat Pattern）**
- リソースとコストを最適化するため、すべてのタスクを毎回実行するのではなく、「最も実行予定から遅れている（overdue）タスク」を優先的に一つだけ実行する戦略が採用されています。
- **モデルのカスケード利用:** 定期チェックのコーディネーター役には、GPT-5 Nano等の安価で高速なモデルを使用し、複雑な推論が必要な場合のみClaude 3.5 Sonnet等の強力なモデルを呼び出す多層構造により、運用コストを抑制しています。

- **静寂と通知の制御**
- LLMが「対応不要」と判断した場合、`HEARTBEAT_OK` トークンを生成して処理を終了します。この場合、ユーザーへの通知は一切行われません。
- 「重要事項あり」と判断された場合のみ、ユーザーに対して通知メッセージ（例：「📧 重要なメールが届いています。返信しますか？」）を生成します。

### 1.3 多層的なイベントトリガー (Multi-Modal Triggers)

定期的なハートビートに加え、OpenClawは非同期な外部イベントにも即応できるアーキテクチャを持っています。

- **Cronサービス:** ユーザー定義のスケジュール（例：「毎朝9時に日報作成」）に基づき、システムイベントを生成します。
- **外部フック（Hooks）:** Google Pub/Sub（Gmail新着通知）やWebhook（GitHub/Stripe等）のエンドポイントを持ち、イベントを受信すると即座にエージェントを起動（Wake up）させます。
- **ファイル監視:** ローカルの特定ファイル（`TODO.md`など）の変更を検知し、自律的にタスクを開始することも可能です。

### 1.4 実行ループと「Loop-until-Done」

エージェントの思考と行動は、`pi-agent-core` ランタイム内の `agentLoop` 関数によって制御されています。

- **ゲートウェイとレーン・キュー（Lane Queue）**
- すべてのトリガー（ユーザー入力、ハートビート、フック）は、セッションごとの「メッセージキュー（レーン）」に投入されます。
- **シリアル実行:** 競合状態（Race Condition）を防ぐため、同一レーン内のタスクは必ず直列に処理されます。エージェントが実行中の場合、次のハートビートは待機またはスキップされます。

- **Agent Loopの4ステップ**

1. **コンテキスト構築:** 過去の履歴、システムプロンプト、現在のツール定義を統合し、LLMへ送信。
2. **意思決定:** LLMは「回答生成」か「ツール実行」かを判断します。
3. **ツール実行:** ツール呼び出し（Tool Call）が含まれる場合、コマンド実行やファイル操作を行い、その結果（Observation）をコンテキストに追記します。
4. **再評価:** 結果を踏まえてステップ1に戻ります。これを「完了」と判断するまで繰り返します。

- **Human-in-the-Loop（人間介在）による安全性**
- 高リスクな操作（メール送信、決済、ファイル削除等）に対し、エージェントは自律的に「実行」するのではなく、`ask_user` ツールを用いて「提案」を行います。
- ユーザーがチャットで承認（`/approve` や "OK"）して初めてアクションが確定するため、能動的でありながら暴走のリスクを最小限に抑えています。

ありがとうございます。第1章の「能動的動作」に続き、第2章ではOpenClawが長期間にわたる文脈をどのように維持し、過去の出来事を「思い出す」のか、その独自の**「記憶システム（Memory System）」**について解説します。

# OpenClaw 技術深層解析：第2章

## ファイル・ファーストな記憶システムとハイブリッド検索技術

OpenClawの記憶力は、複雑な外部データベースではなく、「テキストファイルこそが真実のソースである」という**File-First（ファイル・ファースト）**の哲学に基づいています。
本章では、ユーザーが直接編集可能な記憶構造、ベクトルとキーワードを組み合わせた検索アルゴリズム、そしてコンテキスト溢れを防ぐ圧縮メカニズムについて詳述します。

### 2.1 ファイル・ファーストの哲学と記憶階層

OpenClawは、すべての記憶を人間が可読なMarkdown形式で保存します。これにより、ユーザーはエディタで直接 `MEMORY.md` を書き換えることで、エージェントの記憶を修正したり、新しい知識を強制的に注入したりすることが可能です。

記憶は主に以下の3つの層で管理されています。

- **短期記憶 (Ephemeral / Daily Logs):**
- 場所: `memory/YYYY-MM-DD.md`
- 役割: その日の出来事、実行したコマンド、決定事項を時系列で追記します。セッション開始時に、当日と前日のログが自動的にコンテキストにロードされます。

- **長期記憶 (Durable / Core Memory):**
- 場所: `MEMORY.md`
- 役割: ユーザーのプロフィール、プロジェクトの規約、長期的な目標など、恒久的に保持すべき情報の要約です。ここには「重要な事実」のみが抽出されて保存されます。

- **セッション履歴 (Session Archives):**
- 場所: `sessions/*.md` (および `.jsonl`)
- 役割: 過去のすべての会話の生ログ。これらはスラグ化されて保存され、後述する検索エンジンのインデックス対象となります。

### 2.2 ハイブリッド検索エンジン (SQLite + Vector)

膨大なテキストログから必要な情報を瞬時に引き出すため、OpenClawは **SQLite** を基盤としたハイブリッド検索システムを実装しています。

- **ベクトル検索 (Vector Search / 70% Weight):**
- `sqlite-vec` 拡張を使用し、テキストを埋め込み（Embedding）ベクトル化してコサイン類似度を計算します。
- 「意味的な検索」に強く、例えばユーザーが「あのサーバー」と言ったときに、具体的なホスト名やIPアドレスが含まれるログをヒットさせることができます。

- **キーワード検索 (BM25 / 30% Weight):**
- SQLiteの全文検索機能 `FTS5` を使用します。
- 「完全一致」に強く、特定のエラーコード（例：`ERR_CONNECTION_REFUSED`）や関数名、IDなどを正確に検索する場合に威力を発揮します。

- **スコアリングの工夫:**
- OpenClawは、一般的な検索システムで使われる RRF（Reciprocal Rank Fusion）を採用していません。RRFは順位のみを考慮しスコアの大きさを無視するため、ベクトル検索による「極めて高い意味的一致」の信号を薄めてしまうからです。
- 代わりに、加重平均を用いた独自のスコアリング式を採用し、意味的な関連性を重視する設計となっています。

### 2.3 記憶の整理：事前圧縮フラッシュ (Pre-Compaction Flush)

LLMのコンテキストウィンドウ（記憶容量）には限りがあります。会話が長くなり溢れそうになった際、OpenClawは**「サイレント・エージェンティック・ターン」**と呼ばれる処理をバックグラウンドで実行します。

1. **閾値検知:** コンテキスト使用量が設定値（例：80%）を超えるとトリガーされます。
2. **情報抽出:** LLMに対し、「これまでの会話から、将来重要となる事実を抽出せよ」という内部指示（フラッシュ・プロンプト）を送ります。
3. **永続化と削除:** 抽出された情報は `MEMORY.md` や日次ログに書き込まれ、古い生の会話ログはコンテキストから破棄されます。

このサイクルにより、エージェントは数週間前の会話であっても「要点」だけは決して忘れることなく、あたかも無限の記憶を持っているかのように振る舞います。

### 2.4 システム・プロンプト・ビルダー (Context Injection)

検索された記憶は、どのようにしてエージェントの「脳」に届けられるのでしょうか。これを担うのがレイヤー3の**システム・プロンプト・ビルダー**です。

- エージェントが思考を開始するたびに、ビルダーは以下の要素を動的に結合してプロンプトを生成します：

1. **User Profile:** `USER.md` から読み込んだユーザーの好み。
2. **Dynamic Context:** 現在の会話に関連する、ベクトル検索でヒットした過去の記憶スニペット。
3. **Tool Definitions:** 現在利用可能なツール（MCPサーバーやローカルコマンド）のリスト。

これにより、エージェントは「今、誰と、どのような文脈で話しているか」を完全に理解した状態で応答を生成することができます。

ありがとうございます。第1章の「能動的動作」、第2章の「記憶システム」に続き、最後となる第3章では、自律型エージェントを実運用する上で避けて通れない**「セキュリティとコスト管理」**、そしてOpenClawが目指す**「インフラとしてのAI」**というビジョンについて解説します。

# OpenClaw 技術深層解析：第3章

## セキュリティアーキテクチャと運用課題

24時間稼働し、シェルコマンドやファイル操作の権限を持つ自律型エージェントは、強力であると同時に重大なセキュリティリスクを孕んでいます。OpenClawはこれらのリスクを管理するために、「レーン・キュー」による分離と、厳格なサンドボックス戦略を採用しています。

### 3.1 レーン・キュー (Lane Queue) による競合回避と分離

OpenClawは、複数のタスクが同時に走る環境下でのデータ破損やコンテキストの混濁を防ぐため、**「レーン（Lane）」**という概念を導入しています。

- **セッション分離:** 各チャットルームやユーザーごとに独立したレーンが割り当てられます。これにより、あるユーザーのコンテキストが別のユーザーの処理に混入する「クロス・コンタミネーション」を防止します。
- **シリアル実行 (Serial Execution):** 同一レーン内では、タスクは必ず**直列（一つずつ）**に処理されます。
- 例えば、ハートビートによる「日報作成」と、ユーザーからの「ファイル修正指示」が重なった場合でも、片方が完了するまでもう片方は待機します。
- これにより、複数の自律プロセスが同時に同一ファイルを書き換えて破壊する「レースコンディション（競合状態）」を回避しています。

### 3.2 脆弱性とサンドボックス戦略

2026年2月に発覚した脆弱性（CVE-2026-25253）は、自律型エージェントの危険性を浮き彫りにしました。OpenClawはこの教訓から、現在は多層的な防御策を推奨しています。

- **1-Click RCE (Remote Code Execution) の教訓:**
- 初期の実装では、認証トークンが漏洩しやすく、攻撃者が外部からゲートウェイを操作して任意のコードを実行できる脆弱性がありました。
- **対策:** 現在はゲートウェイを `localhost (127.0.0.1)` にのみバインドし、外部からのアクセスには**SSHトンネル**を必須とする構成が標準化されています。

- **Dockerサンドボックス:**
- エージェントが実行するシェルコマンドは、ホストOS上で直接走らせるのではなく、隔離された **Dockerコンテナ** 内で実行することが推奨されます。
- 万が一エージェントが暴走したり乗っ取られたりしても、ホストマシンの重要ファイルにはアクセスできない仕組みです。

- **Human-in-the-Loop (承認フロー):**
- 「メール送信」「決済」「ファイル削除」などの高リスク操作は、エージェントが独断で行えないようコードレベルで制限されています。
- エージェントは `ask_user` ツールで許可を求め、人間が `/approve` コマンドを実行して初めてアクションがトリガーされます。

### 3.3 コスト管理とモデル・カスケード

「常時起動」のエージェントはAPIコストが膨大になりがちです。OpenClawは経済的な持続可能性を確保するため、以下の技術的な工夫を凝らしています。

- **モデル・カスケード (Model Cascading):**
- すべての判断に最高性能のモデル（Claude 3.5 Sonnetなど）を使うわけではありません。
- 定期チェックや単純なルーティングには、安価で高速な **GPT-4o mini** や **Gemini Flash** 等を使用し、複雑な推論が必要な局面でのみ上位モデルに切り替えるロジックを実装しています。

- **セマンティック・スナップショット:**
- ブラウザ操作を行う際、画面全体のスクリーンショット（画像）をLLMに送るとトークン消費が激しくなります。
- OpenClawは、DOMツリーやアクセシビリティ・ツリーをテキスト化して送る「セマンティック・スナップショット」を活用し、視覚情報を軽量なテキスト情報に変換して処理しています。

### 3.4 結論：インフラストラクチャとしてのAI

OpenClawの設計思想を総括すると、これは単なる「賢いチャットボット」ではなく、**「信頼性の高いインフラストラクチャ」**を目指していることが分かります。

- **確実なトリガー:** ハートビートとCronによる「忘れない」仕組み。
- **永続的な記憶:** ファイルベースの透明性の高い記憶構造。
- **自律と制御のバランス:** Human-in-the-Loopによる安全な実行。

ユーザーが「問いかけずとも予定やメールを確認し、重要なときは通知してくれる」体験は、これら個別のコンポーネントがシームレスに連携した結果です。OpenClawは、個人のPC上に住まう「デジタル・ツイン」としての実用的な解を提示しており、今後のAIエージェント開発の標準的なリファレンスとなるでしょう。
